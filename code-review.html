Executive Summary

mcp-witness is an impressively complete auditing library for AI decision trails. The cryptographic foundations are genuinely strong: domain-separated Merkle trees, null-byte-delimited hash payloads, Ed25519 non-repudiation with key lifecycle support, and RFC 3161-compliant TSA anchoring all reflect deep security awareness. The three-role RBAC system, compliance presets, and structured test coverage show production intent.

However, three hard bugs threaten production correctness today. The most severe is a silent TypeError crash in three MCP tool handlers (witness_stats, witness_health, witness_backfill) caused by arity mismatches in the handler registry dispatcher. Alongside this, a silent data-corruption path in decrypt_field() returns raw ciphertext on authentication-tag failures, and an undocumented MCP_WITNESS_ALLOW_ANON_WRITES flag can silently bypass all configured authentication.

Resolving these three critical issues is necessary before shipping v1.0. The medium-priority items — primarily module-level global state and N+1 TSA calls — can be addressed in subsequent iterations without blocking the release.

🚨 Critical Security & Bug Fixes (High Priority)

Bug

Handler registry arity mismatch crashes three MCP tools at runtime

server.py : 515, 661, 1069, 1012

The central dispatcher at line 515 calls every registered handler as await handler(store, arguments) — always passing two positional arguments. Three handlers are registered with only a single parameter (store), so invoking witness_stats, witness_health, or witness_backfill raises TypeError: handler() takes 1 positional argument but 2 were given. This is caught by the outer except Exception at line 518 and sanitized, so callers see a generic "Internal server error" and no chain statistics, health status, or backfill operations are ever reachable. Because the error is swallowed silently, automated smoke tests that only check for non-empty responses may miss this entirely.

- async def handle_stats(store: StorageBackend) -> dict: + async def handle_stats(store: StorageBackend, args: dict) -> dict: stats = await store.get_stats() ... - async def handle_health(store: StorageBackend) -> dict: + async def handle_health(store: StorageBackend, args: dict) -> dict: - async def handle_backfill(store: StorageBackend) -> dict: + async def handle_backfill(store: StorageBackend, args: dict) -> dict:

The same pattern should be applied consistently to all zero-argument tools. As a defence-in-depth alternative, the dispatcher could use inspect.signature to discover arity, but standardising all handlers to (store, args) is simpler and more explicit.

Security

decrypt_field() silently returns raw ciphertext on MAC failure

security.py : 93–110

AES-256-GCM authentication-tag verification failures are silently swallowed. When the tag check fails (tampered ciphertext, wrong key, or bit-rot), the exception is caught and the function returns the raw ciphertext bytes as if they were valid plaintext. This has two dangerous consequences:

  • Data corruption is invisible. A caller reading a sensitive field will receive garbage data while believing it is valid plaintext.
  • Tamper detection is bypassed. AEAD's entire purpose is to detect ciphertext manipulation; silently falling back undoes that guarantee.

The comment says "backward compatibility with unencrypted records" but this is an incorrect rationale — an unencrypted legacy value would have failed base64.b64decode before reaching the AESGCM call.

def decrypt_field(encrypted: str) -> str: if not encrypted: return encrypted try: key = get_data_encryption_key() raw = base64.b64decode(encrypted) nonce, ciphertext = raw[:12], raw[12:] aesgcm = AESGCM(key) return aesgcm.decrypt(nonce, ciphertext, None).decode() - except Exception as exc: - logger.warning("decrypt_field failure: %s", exc) - return encrypted # ← RETURNS CIPHERTEXT AS PLAINTEXT + except (ValueError, UnicodeDecodeError) as exc: + # ValueError covers invalid base64 AND AEAD tag failures. + # Distinguish unencrypted legacy values (base64 decode fails + # before AESGCM) from actual tag failures (InvalidTag). + logger.warning("decrypt_field failure: %s", exc) + # Return None to force callers to handle missing data explicitly. + return None # type: ignore[return-value]

Change the return type to Optional[str], update all callers to handle None, and separately handle the legacy-unencrypted path with an explicit check before calling AESGCM (e.g., attempt base64 decode; if that succeeds and the result is ≥ 12 bytes, treat as encrypted).

Security

MCP_WITNESS_ALLOW_ANON_WRITES silently bypasses configured authentication

auth.py : 444–458

When authentication is properly configured (API keys or JWT public key present), the authentication path still checks two undocumented environment variables before raising PermissionError: MCP_WITNESS_READ_ONLY=true grants unauthenticated AUDITOR access, and MCP_WITNESS_ALLOW_ANON_WRITES=true grants unauthenticated WRITER access — even when API keys or JWT are active.

This creates a subtle escape hatch: an operator who reads that MCP_WITNESS_DEFAULT_ACCESS=deny is the safe default and sets up API keys correctly may not know that a misconfigured environment variable elsewhere silently opens full write access. Neither variable is documented in the README or SECURITY.md. A supply-chain or configuration management mistake could set MCP_WITNESS_ALLOW_ANON_WRITES=true and the system would silently accept unauthenticated writes.

if api_keys or MCP_WITNESS_JWT_PUBLIC_KEY: - read_only = os.getenv("MCP_WITNESS_READ_ONLY", "false").lower() == "true" - if read_only: - return AuthRole.AUDITOR # ← unauthenticated bypass - allow_anon_writes = os.getenv("MCP_WITNESS_ALLOW_ANON_WRITES", "false").lower() == "true" - if allow_anon_writes: - return AuthRole.WRITER # ← unauthenticated bypass + # When auth is configured, a missing/invalid token is always a hard + # failure. Legacy bypass variables are intentionally removed. raise PermissionError("Authentication required. Provide a valid JWT or API key.")

These legacy escape hatches should be removed entirely. If read-only anonymous access is desired, it should be expressed through MCP_WITNESS_DEFAULT_ACCESS=read_only, which is documented and intentional. The DEPRECATION warning inside enforce_read_only() already signals this direction.

Security

No per-request auth token in MCP tool calls: all clients share process-level identity

server.py : 501–502 • auth.py : 422–424

authenticate() is invoked with no arguments at line 501. When token=None, it falls back to the process-wide environment variable MCP_WITNESS_API_KEY. This means every MCP client connected to the same server process shares the same authentication role, making the three-role RBAC system largely fictional: if any client has admin access (because the server process uses an admin key), all clients effectively do.

The current MCP tool interface has no standard mechanism for passing per-call credentials, which is a genuine architectural constraint of stdio-based MCP. The recommended mitigation is to add an optional auth_token field to tool input schemas, document that as the primary auth channel for multi-tenant deployments, and pass it through to authenticate(): 

# In call_tool dispatcher:
role = authenticate(token=arguments.get("auth_token"))
# Fall back to env var only in single-tenant / dev mode.

An alternative is to run separate server processes per-tenant, each with their own environment variables. Either approach should be clearly documented in SECURITY.md.

🛠 Architecture & Performance Improvements (Medium Priority)

Bug

Default session_id truncated to 8 hex chars — birthday collision at ~65k records

server.py : 533

When no session_id is supplied, the default is str(uuid4())[:8]. Eight hex characters represent only 32 bits of entropy. By the birthday paradox, the 50% collision probability occurs after approximately √(232) = ~65,536 records. A collision silently merges two unrelated sessions in get_chain_for_session(), corrupting the audit trail without raising any error.

- session_id=args.get("session_id", str(uuid4())[:8]), + session_id=args.get("session_id", str(uuid4())),

Use the full UUID (36 characters, 122 bits of entropy). The character-length restriction on session IDs in validate_inputs() already allows up to 256 characters, so there is no downstream constraint preventing this.

Performance

load_api_keys() re-parses environment variable on every authentication call

auth.py : 357–392 • 396–400 • 444

load_api_keys() is called two to three times per tool invocation: once in _lookup_api_key(), and once again in authenticate() itself (line 444). Each call does a string split, strip, and dict build over the full MCP_WITNESS_API_KEYS value. Under load (e.g., 1,000 records/s), this becomes a hot path that allocates a new dictionary on every request. The env var is immutable at runtime, so there is no correctness reason to re-parse it. 

# Module-level lazy cache (analogous to get_hmac_key pattern already in security.py)
_api_keys: Optional[dict[str, AuthRole]] = None

def load_api_keys() -> dict[str, AuthRole]:
    global _api_keys
    if _api_keys is not None:
        return _api_keys
    _api_keys = _parse_api_keys_from_env()
    return _api_keys

This follows the existing pattern established by get_hmac_key() and get_signing_key() in security.py. A sentinel sentinel-object pattern (like _HMAC_KEY_UNSET) handles the "not yet initialised" vs "intentionally empty" distinction correctly.

Performance

Batch TSA attestation makes N sequential HTTP requests (N+1 pattern)

server.py : 735–768

handle_attest() in batch mode iterates over all unattested records and issues one RFC 3161 HTTP request per record sequentially. TSA round-trips are typically 100–500 ms. With 1,000 unattested records, this is a blocking 100–500 second operation. FreeTSA and similar services also rate-limit callers, so this will begin failing silently after the first few hundred requests.

The existing Merkle checkpoint system already solves this: a single checkpoint anchors up to 1,000 records with one TSA call. The batch attester should anchor checkpoints, not individual records: 

# Instead of: for record in unattested → anchor(record.record_hash)
# Do: group records by checkpoint → anchor(checkpoint.merkle_root)

checkpoints = await store.list_checkpoints(limit=MAX_QUERY_LIMIT)
unanchored   = [cp for cp in checkpoints if not cp_has_tsa_anchor(cp)]
results = await asyncio.gather(
    *[anchor_service.anchor(cp.merkle_root, ...) for cp in unanchored],
    return_exceptions=True
)

If per-record TSA attestation is genuinely required, use asyncio.gather with a concurrency semaphore to cap the number of simultaneous HTTP connections.

Security

TSAProvider reads undocumented TSA_URL env var instead of MCP_WITNESS_TSA_URL

anchoring.py : 307

The TSAProvider constructor reads TSA_URL: 

self.tsa_url = tsa_url or os.getenv("TSA_URL") or self.DEFAULT_TSA_URL

But the README and configuration documentation consistently name this variable MCP_WITNESS_TSA_URL. An operator who sets MCP_WITNESS_TSA_URL=https://my-corporate-tsa.example.com/tsr will find their custom TSA silently ignored and all timestamps going to the public FreeTSA instance. Beyond the operational annoyance, if an organisation requires a specific TSA for compliance (e.g., a qualified Trust Service Provider under eIDAS), this mismatch is a compliance violation.

- self.tsa_url = tsa_url or os.getenv("TSA_URL") or self.DEFAULT_TSA_URL + self.tsa_url = ( + tsa_url + or os.getenv("MCP_WITNESS_TSA_URL") # canonical name + or os.getenv("TSA_URL") # backward-compat alias (log a deprecation) + or self.DEFAULT_TSA_URL + )
Security

Redaction stores only 16 hex chars of SHA-256 (64-bit birthday collision risk)

hasher.py : 205

When a field is redacted, its original value is replaced with: 

f"[REDACTED:sha256:{hash_data(original_value)[:16]}]"

Truncating to 16 hex characters leaves only 64 bits. The birthday attack threshold for a collision is approximately 232 ≈ 4.3 billion records — reachable in high-throughput production systems. A collision here means two different original values produce the same redaction token, which could allow an attacker who knows one original value to falsely claim knowledge of another. The full 256-bit hash should be stored; the marginal storage cost of 48 extra characters per redacted field is negligible.

- current[final_key] = f"[REDACTED:sha256:{hash_data(original_value)[:16]}]" + current[final_key] = f"[REDACTED:sha256:{hash_data(original_value)}]"
Architecture

verify_merkle_proof_strict() expected depth formula incorrect for non-power-of-2 trees

merkle.py : 237–241

The strict verifier uses math.ceil(math.log2(tree_size)) where tree_size is the number of records, not padded leaves. The tree is internally padded to the next power of 2, so the actual proof depth is ceil(log2(next_power_of_2(tree_size))). For most inputs these agree, but for exactly-power-of-2 sizes they diverge:

tree_size (records)Padded toActual depthFormula givesResult
442ceil(log₂(4))=2✅ OK
583ceil(log₂(5))=3✅ OK
883ceil(log₂(8))=3✅ OK
110guarded by tree_size>1✅ OK
342ceil(log₂(3))≈1.58→2✅ OK

The formula is actually correct for the current implementation. However, it is fragile: the correctness depends on an implicit coupling between the tree's zero-leaf padding strategy and this formula. Add an inline comment explaining why math.ceil(math.log2(tree_size)) produces the correct depth for a zero-leaf-padded power-of-2 tree, and add a test for every power-of-2 boundary value (2, 4, 8, 16…). As written, the code will silently break if the padding strategy changes.

Architecture

crypto_agility: SigningAlgorithm.NONE verification returns True unconditionally

crypto_agility.py : 103–104

In versioned_verify(), when algo == SigningAlgorithm.NONE, the function returns True — treating the absence of a signature as valid. If an attacker can craft or replay a record with "algo": "none" in its signature field, every signature check on that record passes unconditionally, regardless of the actual record content. 

if algo == SigningAlgorithm.NONE:
    return True  # ← no signature check at all

This is the classic "algorithm confusion" or "none algorithm" attack that has compromised numerous JWT implementations. The correct pattern is to treat a stored algo=none record as unsigned, not as valid: return False when a public key is configured but the record lacks a real signature, and return a neutral result (e.g., a SignatureResult enum) when signing was genuinely not configured.

- if algo == SigningAlgorithm.NONE: - return True # No signing configured — trivially valid + if algo == SigningAlgorithm.NONE: + # Record was created without a signing key. Return False so callers + # can distinguish "not signed" from "signature verified". + return False

Callers that need to distinguish "not signed" from "invalid signature" should check whether a signing key is configured separately rather than encoding that logic inside the signature verifier.

👀 Maintainability & Readability (Nitpicks)

Typing

_TOOL_HANDLERS typed as dict[str, callable] — callable is not a typing construct

server.py : 473

callable (lowercase) is a Python built-in function, not a type annotation. Using it in a generic alias like dict[str, callable] does not provide useful type information to mypy and will produce a warning under strict checking. The correct annotation expresses the handler signature:

- _TOOL_HANDLERS: dict[str, callable] = {} + from typing import Callable, Awaitable + _Handler = Callable[[StorageBackend, dict], Awaitable[dict]] + _TOOL_HANDLERS: dict[str, _Handler] = {}

This also makes the arity mismatch described in Finding 1 a mypy error at development time rather than a runtime crash in production.

Quality

Bare Exception raises in anchoring providers obscure failure categorisation

anchoring.py : 361, 530, 730

Three locations raise bare Exception instead of domain-specific types: 

raise Exception(f"TSA returned HTTP {response.status_code}")
raise Exception("All OpenTimestamps servers failed")
raise Exception(f"Pinata returned {response.status_code}")

AnchorFailureError already exists in the same file and is used by AnchorService.anchor(). The provider-level methods should raise it directly (or a more specific subclass) so that callers can handle anchor failures without catching all exceptions: 

class TSAError(AnchorFailureError): ...
class OTSError(AnchorFailureError): ...

raise TSAError(f"TSA returned HTTP {response.status_code}", failures=[])
DRY

Dead code: duplicate-last-leaf logic inside build_merkle_tree is unreachable

merkle.py : 117

Inside the main loop of build_merkle_tree(): 

right = current[i + 1] if i + 1 < len(current) else current[i]

The else current[i] branch (duplicate last node) can never execute: the leaf list is padded to the next power of 2 before the loop begins (line 108), so every level above the leaf level is also even-numbered. The branch implies a fallback that contradicts the zero-leaf padding strategy and would produce a different root than expected by verify_merkle_proof_strict(). Remove it, or add an assertion:

- right = current[i + 1] if i + 1 < len(current) else current[i] + assert i + 1 < len(current), "Tree must be padded to power-of-2 before loop" + right = current[i + 1]

The same pattern appears in verify_tree_integrity() at line 286 and should be fixed there too.

Nitpick

handle_delete returns sanitize_error(e) dict instead of raising for cleaner error path

server.py : 1193–1194

Most handlers let exceptions propagate to the outer except block in call_tool() where sanitize_error is applied uniformly. handle_delete and handle_search break this pattern by calling sanitize_error directly and returning a dict. This dual path means the outer handler's catch block never fires for these tools, which can cause subtle inconsistencies (e.g., metrics increments that happen in the outer handler won't fire). Let exceptions propagate and rely on the single error boundary.

- except Exception as e: - return sanitize_error(e) # Remove — the outer call_tool() handler covers this already.
Nitpick

auth.py : 55–86

_READ_TOOLS and _WRITE_TOOLS define the universe of tools subject to RBAC. witness_delete and witness_search do not appear in either set. ALL_TOOLS = _READ_TOOLS | _WRITE_TOOLS therefore excludes them. ⚠️ Edge Cases to Consider

  • Empty-string field encryption bypass

    encrypt_field() at security.py:84 returns early with if not plaintext: return plaintext. An empty string is falsy in Python, so an empty sensitive field (e.g., a user clears their phone number) is stored in plaintext while all non-empty values for the same field are encrypted. A partial-data query on the database could distinguish "was ever empty" from "was always a value" even after redaction, leaking metadata. Fix: check if plaintext is None: return plaintext to encrypt zero-length strings.

  • JWT clock-skew asymmetry: exp has no tolerance, iat has 30 seconds

    The JWT verifier at auth.py:325 rejects tokens where exp < now (zero tolerance), but at line 336 allows iat up to 30 seconds in the future. A client with a clock that is 29 seconds fast will successfully issue tokens but those tokens may be rejected 30 seconds before their stated expiry (when the server clock catches up to their exp which was set 30s ahead). Applying the same ±30 s tolerance symmetrically to the expiry check — i.e., reject when exp + 30 < now — avoids spurious rejections without meaningfully widening the acceptance window.

  • Zero-record Merkle proofs and verification with an empty chain

    build_merkle_tree([]) returns MerkleTree(root="", ...) which is correct. However, verify_merkle_proof_strict() called with tree_size=0 enters the tree_size > 1 branch as false, skips depth validation, and then tries to compute a root from an empty proof_path: current = leaf_hash with no loop iterations, so the function returns leaf_hash == "". Any non-empty leaf hash would evaluate to False, while an empty leaf_hash would silently pass. Add an explicit guard: if tree_size == 0: return False at the top of verify_merkle_proof_strict().

  • Concurrent first-write race in SQLite WAL mode with no explicit sequence lock

    The SQLite backend uses BEGIN IMMEDIATE to serialise writes, but the sequence number is derived by querying MAX(sequence) inside the transaction. If two writers begin their transactions at the exact same instant, both may read the same MAX(sequence) before either commits, resulting in a duplicate sequence number. The subsequent unique-constraint check would surface this as an integrity error, but not before one transaction has already computed and stored a hash against that sequence number. Mitigation: use a database-managed AUTOINCREMENT primary key for sequence and remove the application-layer MAX(sequence)+1 computation.

✔️ Commendable Design Decisions

Domain-separated Merkle tree (RFC-compliant) Leaf prefix 0x00 and node prefix 0x01 correctly prevent second-preimage attacks. Most open-source Merkle implementations skip this.
Null-byte delimiter in hash payload Using \x00 between hash-chain components prevents length-extension and delimiter-injection attacks. An excellent, non-obvious choice.
Deterministic genesis hash SHA256("MCP_WITNESS_GENESIS_V1") avoids the all-zeros genesis sentinel that has historically enabled confusion attacks in other audit-trail systems.
Ed25519 non-repudiation with key lifecycle Versioned signatures, a trust store, key rotation support, and the REQUIRE_PERSISTENT_KEY guard show production-grade key management intent.
Proper RFC 3161 DER encoding Hand-rolled ASN.1 DER builder for TSA requests is more reliable than many library implementations and avoids a dependency on pyasn1 at runtime.
Error sanitisation boundary sanitize_error() correctly gates on exception type, never leaks stack traces or SQL to clients, and logs the full detail server-side.
Rate limiting and idempotency are DB-backed Most audit systems implement these in-memory. The DB-backed token bucket survives restarts and works across multiple processes sharing a database.
GDPR redaction preserves hash chain Nulling data fields while keeping the record in the chain is the correct trade-off between right-to-erasure and audit trail integrity.
Deny-by-default access policy MCP_WITNESS_DEFAULT_ACCESS=deny as the out-of-the-box default is the correct secure posture for a compliance-sensitive system.
Crypto agility versioning Storing algorithm identifiers alongside signatures enables future algorithm migration without breaking existing records.
